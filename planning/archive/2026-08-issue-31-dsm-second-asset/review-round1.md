## Findings

### 1. [bug] `scripts/detect_changes.R:127-132` — the refreshed DSM listings are discarded on a no-DEM-change month

Step 5b writes `data/urls_dsm.txt` and `data/dsm_groups.txt` unconditionally, and
the comment says they are "refreshed on every run". That is true locally and
false in CI. `.github/workflows/update.yml`'s **Commit refreshed caches** step is
gated on `steps.detect.outputs.changes == 'true'`, which is only set when
`detect_changes.R` exits **1**. A month in which DSM rasters are added (or a
`.laz`-only delivery gains rasters) while the DEM set is unchanged exits **0**,
the workflow succeeds, and both refreshed files die with the runner.

The result is precisely the stale pairing input the Step 5b comment says it
exists to prevent: `data/dsm_groups.txt` in git keeps saying a mapsheet-year has
no raster DSM long after one landed, and every tile in it stays `no_raster_dsm`.

Compounding it: `scripts/dsm_pair.py` is **not invoked anywhere in
`update.yml`**, so `data/dem_dsm_pairs.csv` is only ever regenerated by hand.
`scripts/item_create.py:69` (unstaged) logs a warning and continues when the csv
is missing, i.e. the DSM asset silently disappears from every new item rather
than failing the run.

Fix: either make the DSM refresh part of the exit contract (exit 1 when the DSM
listing changed too), or drop the `changes == 'true'` gate on the commit step and
let `git diff --cached --quiet` be the only guard — it already handles the
"nothing changed" case. And add a `dsm_pair.py` step to the workflow.

### 2. [bug] `scripts/urls_listing.R:25,70` — the DSM listing has no ratchet; only the DEM set does

Two guards protect this walk and neither covers DSM volume:

* `KEYS_MIN <- 280000` is **48.7%** of the 575,411 keys I counted today. A walk
  that dies at 60% or 80% sails through it.
* `if (length(dsm) == 0)` is a bare non-empty check. One surviving DSM key passes.

The DEM side has a real ratchet — `detect_changes.R:72` refuses anything under
90% of the cached count. The DSM side has nothing equivalent, and
`detect_changes.R:128-129` then overwrites `urls_dsm.txt` / `dsm_groups.txt`
unconditionally because "reaching here means the values are trustworthy". They
are only trustworthy with respect to the *DEM* count.

Concretely: a truncated walk that drops a DSM-heavy slice (the bucket is ordered
lexically, so `/dsm/` keys cluster) can leave the DEM count within 90% while
`urls_dsm.txt` loses tens of thousands of keys. Nothing errors; the next
`dsm_pair.py` run reclassifies those tiles as `unpaired` / `no_dsm_dir` and
`item_create.py` drops their `dsm` asset. This is the "a guard must not fail
toward skip" class — the truncated-walk path and the genuinely-shrunk path are
indistinguishable.

Fix: give the DSM listing the same 90%-of-cached ratchet as the DEM listing in
`detect_changes.R` (read the existing `data/urls_dsm.txt` before overwriting it),
and raise `KEYS_MIN` closer to the observed floor.

### 3. [bug] `scripts/stac_utils.py:185,201` — utm zone padding is not normalized, so a real DEM/DSM pair fails to pair

`pair_key` compares the raw `utm` token, and the bucket spells the zone **both
ways**. Verified against today's real listings:

```
DEM  092/092l/2023/dem/bc_092l061_2_1_2_xli1m_utm09_20231027_20231031.tif
DSM  092/092l/2023/dsm/bc_092l061_2_1_2_xli1m_utm9_20231027_20231031_dsm.tif
```

Same group, same `tile_id`, same `dates` tuple — `utm09` vs `utm9` is the only
difference, and the tile is reported `unpaired`. It is the single such case
today, but the split is bucket-wide, not a typo: `data/urls_list.txt` holds 383
`utm09` and 1,815 `_utm9_`; `data/urls_dsm.txt` holds 184 and 1,057. Today's
count is 1 only because most groups happen to be internally consistent; nothing
enforces that, and any future delivery that changes padding between its `dem/`
and `dsm/` folders loses the whole group's DSM assets.

This is the "cross-function consistency for string normalization" class: parse
the zone as an int and key on that (`utm09` → `9`), rather than on the literal
token. It does not loosen the key.

Fails toward `unpaired` (reported, not silent), which is the right direction —
but it is still a tile that loses its DSM asset for no reason.

### 4. [fragile] `scripts/stac_utils.py:119,201` — `pair_key` cannot separate two real DEM date forms

Two shapes in the bucket collapse to the same `pair_key`:

* **YYMMDD dates.** `RE_DATE` requires a `19|20` prefix, so `170529` and `170607`
  both parse to `dates=()`. In `082/082l/2017`,
  `bc_082l024_2_3_3_xl1m_utm11_170529.tif` and `..._170607.tif` — two different
  flight dates — share one key. Same for `082l024_4_1_1`.
* **The `_1` re-issue suffix.** In `083/083d/2019`, `..._2019.tif` and
  `..._2019_1.tif` differ only by a trailing `_1`, which lands in `tail`, matches
  neither `RE_UTM` nor `RE_DATE`, and is discarded.

**In the staged version this is silent.** `collisions` is computed only over
`dsm_by_key` (the DSM side); two DEMs hitting the same key both take
`matches[0]` and nothing reports it. The working tree has already added
`dsm_shared` — that closes the reporting gap and is the right fix.

Remaining concern after that fix: `dsm_shared`'s report text asserts the shape
means "a re-issued DEM beside its original". For `083d` that is true. For
`082l024` it would be **false** — those are two distinct acquisitions, and if
`082/082l/2017` ever gains DSM rasters both DEMs would silently receive the
wrong-date DSM. It is latent only because that group is not in
`data/dsm_groups.txt` today. Consider widening `RE_DATE` to accept the 6-digit
`YYMMDD` form, or keeping the unmatched tail tokens in the key.

Also note the 4 genuinely-distinct collisions sit alongside 36 collision groups
caused by the parenthesized duplicates (`... (2).tif`, `... (3).tif`) that are
still in `urls_list.txt`; they are harmless today only because those files fail
validation and never become items.

### 5. [fragile] `scripts/urls_listing.R:65` — `sub()` returns its input unchanged on no match

```r
dsm_groups <- sort(unique(sub("/dsm/.*$", "", sub("^.*/gdwuts/", "", dsm_any))))
```

If the URL shape ever changes (bucket rename, a different `url_bucket`
argument), the inner `sub` matches nothing and silently emits full URLs as
"groups". Those can never equal `tile_key_parse()`'s `group`
(`082/082e/2018`), so every `.laz`-only tile flips from `no_raster_dsm` to
`no_dsm_dir` — a wrong classification with no error anywhere. Cheap guard:
`stopifnot(all(grepl("^/?[0-9]", dsm_groups)))` or derive the prefix from
`url_bucket` instead of hard-coding `/gdwuts/`.

(The greedy `^.*` is fine today: 8 keys contain the string `gdwuts`, but none as
a `/gdwuts/` path segment and none under `/dsm/`.)

### 6. [fragile] `scripts/dsm_pair.py:186` — the conservation check is an `assert`

The module docstring makes the "counts sum to the DEM input, asserted before
writing anything" invariant load-bearing. `python -O` strips it. CI does not use
`-O` today, so this is low severity, but a bare `if ... raise` costs nothing.

## Probes explicitly requested

1. **`dsm_unmatched = [k for k in dsm_keys if k not in claimed]` — O(n²)?**
   **No.** `claimed` is a `set` (working tree: a `defaultdict`, where `in` also
   does not insert), so membership is O(1) and the comprehension is O(len(dsm_keys))
   ≈ 96k. The whole `pairs_build` is O(n); the real 102,416 × 95,889 run completes
   in a couple of seconds and produced `data/dem_dsm_pairs.csv`. Tractable.

2. **Can `RE_SUBDIVISION = ^\d{1,2}$` greedily consume a non-subdivision token?**
   **Not on any filename in the bucket.** Across all 102,416 DEM and 95,889 DSM
   keys, the consumed run is exactly **0 or 3 tokens** — never 1 or 2, which is
   what a spurious consumption would look like. No key places a bare 1–2 digit
   non-subdivision token immediately after a mapsheet code (resolution tokens are
   `xl1m`/`xli1m`/`xl2m`/`l1m`, the zone is `utmNN`, dates are 4/6/8 digits).
   Not a problem.

   Adjacent, and real in the **staged** version: `RE_MAPSHEET =
   ^\d{3}[a-z]\d{3}$` rejects the 6-digit form (`092h001212`), leaving 1,659 real
   tiles `unparseable` — 1,659 of the 3,904 unparseable keys I measured against
   the staged parser. The working tree has already widened it to
   `^\d{3}[a-z](?:\d{3}|\d{6})$` and unparseable drops to the 2,245
   `albers10k2m` keys, which is correct.

3. **Can the `PRODUCT_TOKENS` strip create a false pair?**
   **No.** `pair_key` is `(group, tile_id, utm, dates)`; none of those is derived
   from `stem` or `product`. Removing a trailing `dem`/`dsm`/`chm` token can only
   shorten `tail`, and that token matches neither `RE_UTM`, `RE_DATE` nor
   `RE_SUBDIVISION`, so `tile_id`/`utm`/`dates` are unchanged by the strip.
   Confirmed empirically: **0** DSM-side `pair_key` collisions across the full
   95,889-key DSM listing. (`stem` and `product` feed only
   `convention_classify`, which is an observation on an already-matched pair.)

4. **Does a utm token present on one side and absent/different on the other
   actually happen?**
   **Yes — 1 case today.** See finding 3. Of the 173 `unpaired` tiles: 154 have no
   DSM with that `tile_id` in the group at all (a genuine gap), 18 fail on
   differing `dates` (`bc_082f0xx_l1m_utm11_20180830.tif` vs
   `..._xli1m_utm11_2017_dsm.tif` — a 2017 DSM against a 2018 DEM, arguably
   correctly not paired), and **1** fails purely on `utm09` vs `utm9`.

5. **Does the final-line-without-newline trap apply to `keys_load`?**
   **No.** `for line in fh` yields the final unterminated line; this is the Python
   equivalent of the `read -r || [ -n "$line" ]` fix, already correct by
   construction. Verified: `data/urls_list.txt` (102,416 newlines, 102,416
   non-blank lines read). The `.strip()`-and-skip-blank pattern is also safe
   against a trailing blank line.

6. **`KEYS_MIN = 280000` and `sub("^.*/gdwuts/", ...)`**
   `KEYS_MIN` is a floor, not a partial-walk detector: 280,000 / 575,411 = 48.7%,
   so anything above half a bucket passes. It does fail loudly (`stop()` inside
   `detect_changes.R`'s `tryCatch` → exit 2, the correct code), so the *contract*
   is right; the *threshold* is loose, and the DEM 90% ratchet is what actually
   catches a realistic partial walk — which is exactly why the DSM side needs the
   same ratchet (finding 2). `urls_fetch.R` has no ratchet at all and writes
   `urls_list.txt` directly, so a 60%-truncated walk there overwrites the cache
   unguarded.
   For the `sub()`: safe today (no key carries `/gdwuts/` as a path segment; the 8
   keys containing the substring are `*_gdwuts_list.csv` files, none under
   `/dsm/`), but see finding 5 for the silent no-match behaviour.

## Checked and clean

* **Exit-code contract.** `source("scripts/urls_listing.R")` is inside the
  `tryCatch`, so a missing/broken helper or a `stop()` from any guard yields
  `"error"` → `quit(status = 2)`. No new top-level code can abort with R's
  default status 1. The header comment explaining *why* is accurate. The
  `readr::`/`fs::`/`ngr::` namespacing convention is preserved in the new file.
* **`ngr::ngr_s3_keys_get(pattern = NULL)`** is supported — the pattern block is
  `if (!is.null(pattern))`, so `NULL` means "no filtering", not "filter with
  NULL". It does `cli_abort` on any non-200, so the "a failed walk raises rather
  than returning `character(0)`" claim in the header holds. No extra HTTP cost
  either: the old patterned call already walked the whole bucket and filtered
  afterwards.
* **Case sensitivity of the R filters.** `grepl("/dsm/", fixed = TRUE)` and
  `grepl("\\.tif$")` are case-sensitive. Checked the full 575,411-key listing: 0
  uppercase `.TIF`/`.Tif`, 0 `/DSM/`, 0 `.tiff`. Safe.
* **No key is in both the DEM and DSM lists** (`set(dem) & set(dsm)` = 0), so the
  "anchored on the product directory" comment on `urls_listing.R:58` is
  load-bearing and correct — nothing can be indexed as its own DSM.
* **No nested `dsm/` subdirectories** (0 keys with a `/` after `/dsm/`), so the R
  `sub("/dsm/.*$")` group and Python `parts[:-2]` group agree on every real key.
* **`no_raster_dsm` vs `no_dsm_dir` ordering** in `pairs_build` is correct
  (raster-groups checked before dir-groups), and the third input genuinely earns
  its keep: it is what turns the 1,211 `.laz`-only tiles into a declared gap.
* **`report_render` division by `total`** cannot hit zero — `keys_load` raises on
  an empty listing first. The `lines += [...] or ["- none"]` precedence is
  correct (`+=` binds after `or`).
* **URL-form agreement.** `fix_url` + `PATH_S3` stripping makes the single-slash
  `https:/` form, the double-slash form and the bare key parse to the same
  `group`; `test_url_forms_agree_on_the_group` covers it, and the real run
  confirms it (95,887 pairs against single-slash inputs).
* No secrets, no shell interpolation, no destructive paths in the diff.
